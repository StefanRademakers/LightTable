Task 264 - Local Codex to LightTable MCP A-Z acceptance route

Status
Active. The isolated launcher and SDK transport proof exist; final acceptance
through a genuinely fresh Codex session remains owner-visible work.

Goal
Run the real LightTable desktop tunnel and a local Streamable HTTP MCP server,
connect a fresh Codex session through opt-in local configuration, and prove a
complete inspect -> create -> edit -> preview -> correct -> save/export flow.

Implemented foundation (2026-08-20)
- `npm run mcp:local:codex` launches an isolated packaged desktop and prints the
  exact opt-in Codex setup/login/removal commands plus the short-lived pairing
  code.
- Codex MCP/OAuth stays on loopback HTTP while the desktop connects separately
  over a one-day localhost HTTPS/WSS endpoint. Production defaults remain one
  HTTPS origin.
- `npm run smoke:mcp:local-codex` uses a separate Streamable HTTP SDK client and
  passed the approval/read/edit/revocation lifecycle against the packaged app.
- The probe exposed and fixed `lighttable_capabilities`: its MCP structured
  content is now the valid object `{ documentId, commands }`, not a bare array.
- Detailed instructions and security boundaries live in
  [`architecture/integrations/LOCAL_CODEX_MCP_ACCEPTANCE.md`](../../../architecture/integrations/LOCAL_CODEX_MCP_ACCEPTANCE.md).

Automated packaged A-Z evidence (2026-08-21)
- `npm run smoke:mcp:local-codex:a-z` uses the real packaged desktop, outbound
  HTTPS/WSS tunnel, loopback Streamable HTTP MCP and explicit approval gates.
- It built a four-layer editable text/vector/effect design, queried canonical
  state, corrected text from revision 4 to 5 and proved changed preview pixels.
- Invalid schema, missing target and stale-revision writes were rejected.
- A fresh SDK connection recovered revision 5 after reconnect; PNG and native
  LightTable artifacts passed their binary signatures and contained no bytes
  in the committed report.
- This closes the automatable product route underneath Codex. It does not turn
  the remaining genuinely fresh Codex-session acceptance into an automated
  claim.

Owner-visible fresh Codex evidence (2026-08-21)
- A genuinely fresh Codex client completed OAuth, explicit read approval and a
  direct read-to-edit permission upgrade through the packaged Agent Access UI.
- Through LightTable MCP only it inspected happy_birthday.png, created a
  separate 1200x1200 8-bit sRGB document, and reconstructed the reference as
  twelve editable raster/vector/text layers. The final bounded preview was
  inspected at canonical revision 22; the reference remained unchanged.
- The run used no paid provider, external generation, source mutation or direct
  application automation. It exposed text stroke/shadow and renderer-settle
  gaps plus a 76-call efficiency baseline.
- Native save/export, Actions observation, independent packaged pixel/layer
  verification and the fresh-client error/reconnect/cleanup cases remain open,
  so Task 264 is not complete.
