Task 207 - Make structural audits reflect product and ownership risk

Goal
====

Make structural audits useful decision support: distinguish cohesive large
systems from mixed-authority orchestration, and connect generated LUTs, models,
Wasm and application chunks to measured delivery/runtime cost rather than an
arbitrary line target.

Current evidence
================

- `audit:source-structure` treats a 68,191-line generated LUT like handwritten
  source, creating noise in the hotspot gate.
- The same 8.6 MB LUT is present in the 11.09 MB initial web JavaScript chunk,
  which is a genuine product cost the line-count audit cannot express.
- Multiple handwritten files exceed existing ratchets and must remain visible.

Implementation contract
=======================

- Classify generated source by a narrow, auditable rule; do not broadly ignore
  large files or treat a lower line count as an improvement by itself.
- Retain byte/checksum accountability for generated artifacts.
- Report initial JS, CSS and lazy heavyweight assets from the production web
  build together with their load boundary and user-flow reason.
- For handwritten hotspots, report responsibility groups, fan-out and lifecycle
  ownership alongside size. Do not require extraction when the file is large
  but cohesive, and do not approve a mixed-authority file merely because it is
  below a numeric ceiling.
- Any enforced delivery budget must be based on a named startup/user-flow goal
  and measured baseline, not selected only to make the current build pass.
- Do not change LUT math or render output in this task.

Definition of done
==================

Generated data no longer corrupts handwritten complexity signals, delivery cost
and ownership concentration are reported in product terms, relevant script
tests pass and the task moves to `work/done` with its implementation.

Completion evidence (2026-08-19)
================================

- Replaced line-cap exceptions with ownership reviews. Eighteen current
  hotspots now record mixed-authority versus cohesive-heavy classification,
  responsibility groups, import fan-out, lifecycle owners, product risk and a
  concrete extraction/retention decision. Size triggers review; material growth
  reopens it, but fewer lines alone cannot satisfy the policy.
- Classified the 68,191-line Color/Vibrance LUT only by exact path, exact
  generated marker and verified generator. It is removed from handwritten
  rankings while retaining 8,591,289 bytes, SHA-256, gzip/Brotli cost, initial
  load boundary and its Grade user-flow reason in the report.
- Added a production web-delivery audit. The fresh build measures 11,222,464
  raw bytes initial JavaScript (4,302,331 Brotli-q6 in the preceding measured
  run) and 302,244 raw bytes initial CSS. Heavy Wasm/model/worker assets map to
  explicit lazy user flows; an unknown heavy asset or a feature-only asset that
  becomes initial fails the audit.
- The delivery regression band is based on that dated build and a named startup
  goal. Documentation explicitly says passing is not evidence that the current
  11 MB-class entry is optimal.
- The quick/full quality profile now runs delivery analysis after the production
  web build, and structural policy tests are part of the root unit suite.
